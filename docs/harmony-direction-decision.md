## 3. 三个选项

| 选项 | 优点 | 代价 |
|---|---|---|
| **A. 转 WebView** | 四个未做模块白送；永不与 web 漂移；剩余工作仅壳子本身 + 安全区/键盘/返回键/深链适配 | 弃用已完成的原生代码；失去 UI 自动化；无后台通知 |
| **B. 继续原生** | 保留全部已有成果与自动化能力；原生体验与后台通知 | 四个模块需逐一移植并持续对齐 web；本阶段已证明对齐成本高（见 §4） |
| **C. 混合**（原生保连接层，WebView 渲染剩余模块） | 理论上兼得 | **不推荐**：两边状态需同步，会成为新的缺陷来源，且同时承担两种方案的成本 |

## 4. 对齐成本的实测证据（B 选项的主要风险）

会话管理这一个阶段中，**由评审发现、且单测与静态守卫全部无法察觉**的 web 偏离：

1. 删除会话与标记已读**从来不可能成功**——`Content-Type: application/json` + 空 body 被 Fastify 在路由处理器之前拒绝。128 个单测与对齐守卫对此结构性失明，由评审起真实服务端才发现。
2. 「sticky 只被自报身份的帧写入」这一前提**对 web 不成立**（web 有六个写入点，客户端只实现了一个），连续存活于三份文档，直接导致新开两个阻塞任务。
3. 自动命名上限写成 20 字，而 web 与服务端**独立地都是 15 字**——会造成客户端命名一次、服务端改回去的来回重命名。
4. 标签解析强制走 `labelOf`，会让一个连接下所有会话行**显示成同一个 bridge 名**。
5. 冷启动时恢复出的会话指针被覆盖成 `default` 并写回磁盘，使持久化功能每次启动被抹掉一次。

这五项都不会让任何测试变红。**它们是「照着另一个实现做」这件事的固有成本，而不是执行不力。**
